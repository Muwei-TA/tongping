同频｜校园社团共同空间

市场调研、产品设计与交互规格 · V1.0 · 2026 年 9 月 21 日

一句话：不再做一个聊天软件，而是让社团成员的作品得到回应、经验被下一届找到、关系在共同活动中生长。

本文是基于公开资料的桌面研究与第一版产品假设，不是已完成的用户访谈或市场验证。原型中的南川大学、人物、社团、作品、人数、活动均为虚构演示数据，不代表真实学校合作或经营指标。

01 / 建议先做的产品，而不是先堆的功能

切入点：创作型社团的“作品反馈 + 知识传承”。活动和轻社交负责让关系继续，而不是一开始同时争夺论坛、即时通信、教务管理和泛娱乐市场。

默认边界是中国大陆高校、单校多社团、微信和 QQ 两个小程序入口。首批可以选择动画、摄影、设计等具有持续作品产出的社团。体育、公益、桌游等组织也可以使用相同底座，但不是第一阶段需要证明的全部市场。先从一个校区的少量组织验证，不能用“每所学校都有社团”直接推出人人会使用。

品牌暂定“同频”，不是已经注册或完成商标检索的名称。产品承诺是“这里有人愿意看，也有人愿意一起做”。它不承诺让用户涨粉、接单、取得学分或获得学校认证。

决策项 第一版建议 为什么这样取舍
核心对象 一个有明确边界的社团共同空间 成员、规则、作品、知识和活动有稳定归属
首要价值 具体反馈，而非单纯曝光 用一次有用回应证明进入新工具的必要性
关系来源 已有组织关系 + 共同参与 不从陌生人匹配和无约束私聊开始
内容原则 社内默认、公开另行授权 降低半成品发布压力，明确传播边界
渠道策略 原群保留，链接进入对应社团和内容 不要求整体搬群，不依赖读取群聊天记录
商业原则 先验证组织留用，再验证谁愿意付费 学生使用者、社长推动者和采购者可能不是同一人

**应当推翻这项建议的情况：**真实访谈发现成员主要缺的是临时通知，而不是反馈与查找；社长无法承担最低治理责任；现有工具已经足够且没人愿意切换；两端所需准入或类目在拟运营主体下不成立。遇到这些情况应缩小到知识交接工具或停止该方向，而不是继续增加功能。

02 / 从第一性原则拆解需求

“发作品、分享知识、互动、娱乐社交”是四组手段，不是四个最终目的。更底层的问题是：一个人为何愿意来到这里，贡献一次，然后再回来？

2.1 五种不可再省的用户价值

底层需求 用户真正要完成的事 产品应提供的最短路径 反例：看似有功能，却没解决问题
被认真看见 给半成品找一个懂的人，获得可执行建议 作品 + 想获得什么反馈 + 对应讨论 只有点赞榜，没人回答具体问题
少走弯路 快速找到已验证的经验、例子和负责人 知识目录 + 搜索 + 维护人 + 更新时间 把所有附件放进一个无限增长列表
安全参与 在明确的人群和规则内表达，不被任意传播 成员权限 + 范围提示 + 举报与申诉 叫“私域”，却能从搜索或分享卡片读到内文
形成归属 和一群人完成一件小事，建立共同记忆 低门槛话题 → 活动 → 回顾 不断推送热搜和陌生人消息
持续运转 毕业、换届之后，资料和责任仍然可接续 组织所有权 + 交接清单 + 双方确认 社团资产都留在某一位社长个人账号

可用一个定性思考式约束设计：

愿意再次参与 ≈ 获得的帮助 + 被认可感 + 归属感 − 发布成本 − 查找成本 − 社交压力

这不是被测量的公式。它的作用是提醒团队：多加一个入口、多要一次授权、多建一种积分，都可能增加右边的成本。

2.2 从约束反推设计

成员注意力有限，因此首页只突出一件值得参与的事，并按有权限的组织展示有限内容；不为了时长做无限推荐。一个人可能同时加入多个社团，因此账号与成员关系必须分离，不能把“登录成功”当成“全校可看”。组织会更换负责人，因此权限是带期限、可撤销的关系，不是写死在用户表中的永久身份。

作品质量与完成度不同，发布表单不能暗示只有成品才配被展示。要求作者写“希望听听哪方面意见”，比强迫选十个分类更接近价值。沉默成员也可能获得帮助，不应通过强制签到或发帖配额把他们赶走。

娱乐社交不必等于新增游戏系统。一次创作小挑战、一个片单投票、一场线下放映、活动后的共同回顾，已经能够承接“认识同伴”的目标。第一版不建立公共魅力值、社交排名或陌生人私信。

03 / 市场调研：替代关系比功能数量更重要

3.1 本次已核实的公开证据

知识星球的官方定位围绕创作者、内容沉淀和社群运营，其公开功能包括多种内容形式、标签与精华、检索及角色管理。这说明“发布 + 知识存储 + 群体管理”已有成熟替代供给，不能仅靠拼出这些功能证明新产品成立。S1

到梦空间官方介绍覆盖活动发布、报名、签到、学分发放、成果评价和第二课堂成绩单。这意味着高校正式活动管理并非空白市场；同频不应在没有校方授权和系统对接的情况下承诺学分、认证或替代既有流程。S2

Discord 官方论坛文档展示了按主题组织讨论、标签、角色权限以及列表/媒体画廊等模式。这里借鉴的是信息组织方式，不是推断其在国内目标学校的普及率，更不是建议直接搬用其运行环境。S3

替代方案 为什么要研究它 同频的应对，不是断言对方做不到
微信 / QQ 现有社团群 用户已指定的入口与关系来源；实际使用习惯待访谈 保留即时沟通，把作品讨论、经验和活动凭证组织起来
知识星球 S1 内容沉淀与社群运营的直接替代 验证“同伴互助、组织换届”是否比创作者中心模式更适合目标社团
到梦空间 S2 校内正式活动管理的相关替代 免费社团小活动与内容回顾互联；遇到正式流程时明确边界
Discord 论坛模式 S3 话题持续讨论与权限组织的结构参考 用中文校园场景压缩入口，不复制复杂频道树
群文件、网盘、共享文档组合 待研究的真实替代工作流，不是已完成的产品测评 观察成员是否能找到旧资料、确认版本和联系维护人；若已足够，则降低替换范围

不能从上述资料得出“这些产品都没有换届功能”或“同频没有竞争对手”。本次没有完成各产品登录后的逐版本全功能测试，也没有可核验的目标人群覆盖率、留存率和付费转化数据。

3.2 最可能成立的市场空隙：需要验证的判断

机会不在于“校园版朋友圈”，而在于把发布者、懂内容的同伴、下一届新人、当前负责人放进同一条可持续协作链。这个判断来自目标场景与替代品侧重点的比较，属于产品推论，不是统计结论。

优先创作型社团，是因为“持续产出 → 点评 → 方法复用”能在一条链上发生，方便用较小样本观察价值。是否确实更适合，需要与非创作型组织对照。不要同时招募十种社团，最后无法判断谁真正留下。

3.3 用户、推动者、决策者、付款人分别是谁

普通成员消费与贡献内容；社长或骨干组织冷启动、审核和交接；指导老师或校方管理者可能影响校内准入；实际支付者可能是社团、院系或项目运营方。这些角色是否存在、是否有预算，都尚未验证。

因此不采用“全国大学生数量 × 单价”估算收入。第一阶段可以设定一个容量实验：1 所学校 × 3 个社团 × 每团约 50 个参与名额 = 150 个成员关系名额。这不是 150 个独立用户，因为一人可能加入多个社团；更不是市场规模或签约预测。

未来的可服务市场应从“有代表权限、真实需求、可持续组织者、允许上线使用的组织数”向上估算。先记录可接触组织、愿意试点、实际启用、持续使用和愿意采购五层漏斗，再讨论收入空间。

04 / 把假设变成可证伪的用户研究

以下研究尚未执行。建议样本结构为 6 名社长/骨干、12 名成员、2 名指导老师或管理者；成员中分别覆盖创作者、普通活跃成员和很少发言者。人数是招募计划，不是调研结果。

要验证的假设 访谈或观察任务 什么结果会改变产品方向
半成品缺少有效反馈 请对方展示最近一次发布及后续回应，讲清如何改进 主要目的只是晒成品，不需要社内反馈
老知识确实难找 现场查找一份上届经验或工程规范，记录过程 现有目录已经满足需求，替换没有价值
成员愿意在私域发布 对比仅社内、校内公开、互联网公开三个范围 即使仅社内也不愿发布，需先处理评价压力
社长愿意治理与交接 展示最近一次入社审批、违规处理或换届交接 没人负责审核，不能用“自治”掩盖运营缺口
双宿主有实际价值 记录受访者真实主要入口、可用设备、跳转失败情境 一个宿主几乎无人需要，先减少适配负担
存在支付理由 找到真实预算人，讨论目前付出的人力和替代费用 只有成员口头喜欢，没有组织持续投入意愿

问题应围绕“最近一次发生的事”，而不是“你觉得这个功能好吗”。不要把访谈中的礼貌肯定当作需求。对原有内容的展示取得许可，只记录去标识的观察结果，不批量复制群聊天、学号、通讯录或未授权作品。

首轮可用性测试建议邀请 5–8 名目标成员独立操作原型，观察三项任务：找到加入入口；发布仅社团可见的作品并说明反馈目标；在不允许通知的情况下完成报名。记录错误、停顿、理解偏差和任务是否完成，而不是只记录界面满意度。第二轮再验证负责人审核与换届。

05 / 核心体验：三个成员闭环，一个组织闭环

A. 加入与第一次贡献

社团群分享入口 → 社团公开介绍 → 宿主登录 + 最少资料 → 阅读社规与申请 → 负责人审核 → 新成员路径 → 一次低压力贡献

游客能看公开介绍，不应为了看一句社团简介就被要求提供资料。宿主登录成功只建立账号，不验证学籍，也不自动授予成员身份。未通过申请的人仍然不能从搜索、历史收藏或别人转发的详情路径进入私域。审批拒绝要给理由，并允许补充信息后重新申请。

第一份贡献可以是给一位作者留下具体反馈，不必强迫新人先有作品。新成员阅读路径建议为“社规 → 一篇新手指南 → 一个作品示例”。原型展示阅读状态，生产版再根据任务完成提供非公开的成长反馈，不发全校排行榜。

B. 创作与反馈

发布作品 / 知识 / 提问 / 闲聊 → 明确希望得到的回应 → 默认仅社内 → 投稿审核 → 可见内容 → 同伴反馈 → 作者阅读或补充 → 可复用经验

四类内容共享一个发布器，但字段语气和辅助提示不同。作品强调附件与反馈目标；知识强调步骤、适用范围和来源；提问强调已经尝试过什么；闲聊强调明确话题。不是四套独立开发的社区。

MVP 的创作质量机制不是审美打分，而是降低回应成本：评论输入框提示“我注意到什么、为什么、可试什么”。反对人身标签和恶意围攻。作品是否优秀不决定能否进入社团；内容安全和授权是否合规才是治理的基本边界。

知识沉淀要经过作者同意：负责人从已发布内容提名，作者确认整理与展示范围，建立维护人、版本和来源关系。**原型仅展示知识库与阅读，不实现这套知识编辑/提名发布流程；这是生产 MVP 需补齐的功能。**不会把一条评论自动转换为平台拥有著作权的“知识资产”。

C. 活动与关系

社团活动 → 详情与规则 → 报名 / 候补 → 个人凭证 → 授权组织者核验 → 活动回顾 → 新作品或新知识

报名不以授予宿主通知权限为前提。容量满时清楚写“候补不是报名成功”，不能同时显示确认入场。取消活动后已有凭证显著失效，站内消息作为可追溯的状态入口，宿主通知只是额外触达，不承诺一定送达。

原型含演示签到按钮，方便理解后续界面；正式版不能把该按钮直接作为成员的自助核销依据。生产版使用组织者权限、一次性凭证、活动有效期和防重放校验。具体安全实现需后端测试。

D. 组织换届

现任负责人核对资料 / 未完活动 / 授权责任 → 选择合格继任者 → 发起交接 → 继任者独立账号确认 → 原子移交 → 撤销旧权限 → 留下审计记录

只移交组织管理责任，不移交个人账号、私人内容或作品著作权。最后一名负责人不能直接退出导致组织无人负责。候选人失去资格、当前所有权变化、凭证过期或双方账号冲突时，交接必须停止并告知下一步。

原型可从“社长”切到“继任者”确认接收，再切回旧社长观察管理台锁定。这只是多账号流程模拟，不是生产权限验证。

06 / 信息架构与前端 UI 设计

底部导航保持五项：动态 / 社团 / 发布 / 消息 / 我的。知识、活动、轻互动从首页快捷入口或社团空间进入；不再把所有栏目挤到一级导航。

“动态”回答今天值得参与什么；“社团”回答内容属于哪个组织、我是什么身份；中央“发布”回答如何留下内容；“消息”回答与我有关的回应和事务；“我的”回答我的作品、收藏、报名、隐私与角色。

6.1 视觉语言

采用暖白纸感底色、森林绿主色和少量浅柠檬绿、杏色、淡紫色。作品页面把图片和反馈目标放在视觉中心；知识页面提高目录与段落可读性；活动页用海报和凭证结构形成区别；管理页减少装饰、突出待办与理由。

字号和间距不是为了“塞下更多”。原型主要按钮采用至少 44 CSS 像素高度，小屏内容可以滚动；所有实际小程序仍需在两端动态字体、系统安全区、辅助阅读和真实触控下复核。本交付没有宣称通过无障碍标准认证。

提示语原则是先解释发生了什么，再给行动。例如“审核中，仅作者和审核员可见”比只写“已提交”更有用；“候补不是报名成功”比绿色“操作成功”更准确；“未加入该社团”不等于“网络错误”。

6.2 原型评审工作台

电脑打开原型，可从左侧 26 页目录跳转，中间体验手机页面，右侧阅读本页目标、组件、点击去向、权限与异常状态。右上角可切换游客、成员、社长、继任者；微信/QQ 选项仅切换宿主预览，不代表已经接入 SDK。

09 / 私域权限、个人信息与治理

9.1 可见性矩阵：建议的生产规则

内容 / 能力 游客 本社成员 社长 / 经授权管理员 平台治理人员
社团公开简介 可看 可看 维护 按职责维护与核验
已授权公开作品 可看 可看；社内讨论资格另判 适用内容治理 适用治理
社内已发布作品、知识、活动 不可看 可看 按组织权限可看 仅因明确治理工单、必要权限访问并留痕
待审核投稿 不可看 仅本人 有对应审核权限者；避免自审 必要复核
入社申请资料 不可看 仅本人 仅负责入社者，不默认全体干事可看 必要治理
本人收藏、通知、报名 不可看 仅本人 无权任意浏览成员私有集合 必要、受控访问

“同校”不等于“同社团”，“好友”不等于“有内容权限”。公开展览与私域成员评论可以采用不同的访问策略，首版至少禁止游客提交社内评论。转发小程序入口不应自动附带私域标题、作者头像或内文；需要相应权限之后再展示。

9.2 数据最少化与权利设计

个人信息保护法规定目的明确、必要和最小范围等原则，并对告知、基于同意的处理、撤回同意、保存期限、公开个人信息和未满十四周岁未成年人信息等作出要求。本方案据此提出产品设计；是否适用于具体业务及如何履行，仍需按运营主体和真实流程专项审查。S5

建议默认只收昵称及建立账号所必需的标识，不默认索取学号、身份证照片、精确定位或通讯录。具体业务如依法需要额外身份核验，应说明目的、法律依据、字段、保存期和访问人，不能因“大学校园”就假设所有用户成年，也不能把普通兴趣字段当作强制登录门槛。

与账号建立、社团加入、内容公开、活动通知有关的选择分开呈现。不要用一个总勾选框把必要服务和可选推广捆在一起。成员能调整通知偏好、发起退出和账号权利请求；退出后有权保留什么、删除什么、匿名化什么，需要明确，不承诺“一键彻底删除所有依法应留存记录”。

创作者保有其作品权利。平台展示、社内分享、选入知识库、公开展览、活动宣传是不同用途，按各自授权处理。涉及他人肖像、音乐、商业素材、学校标识时，上传者声明不足以替代必要核验与投诉处理。

9.3 治理不是上线后的补丁

上线前确定社规、平台规则、举报入口、内容检查服务、人工处理人、应急联系渠道和独立复核机制。小规模试点可以人工前置审核，但必须观察处理延迟；“所有内容等社长下课再看”可能直接毁掉反馈价值。

建议生产流程：提交内容和附件进入隔离区，完成安全检查后按风险分流；需要人工复核的进入队列；发布后仍支持举报、临时限制传播、给理由和独立申诉。具体内容类别、检测接口和审核要求必须结合平台现行政策确认，不能把本原型的本地“通过”当作满足了平台审核义务。

一位社长既发作品又是唯一审核员时，应由另外授权的审核者或平台专岗处理，不能允许本人终审。举报量下降也不一定代表更安全，可能是举报入口难找，应结合处理时长、复核结果和用户反馈判断。

10 / 微信与 QQ 双入口：共享业务，不假设原生能力一致

10.1 先做一个准入与能力验证小样

在正式排期前，用拟上线主体核实两个平台的账号资格、可选服务类目、UGC 内容要求、适用备案/资质、隐私声明、学校授权与审核材料。以当时控制台和官方审核反馈为准；本次没有登录运营主体账号验证，不能承诺两个宿主都能按当前设计直接上线。S6

最先跑通的不是漂亮首页，而是“登录取得服务端会话 → 申请成员资格 → 只读有权内容 → 上传一张受控图片 → 分享一个通用入口 → 拒绝通知后仍可正常使用”。登录、上传、分享、通知任一项不满足要求，都要在产品方案中有降级，而不是用不合规跳转绕过限制。

能力 两端共用部分 单独适配与验收 失败时产品表现
登录 内部用户、会话、成员关系 每个宿主的授权、凭证交换、过期处理 可继续看公开简介；写操作要求重新登录
图文与作品 投稿、附件元数据、审核状态 媒体选择、压缩、上传限制、预览 保留草稿；明确哪个附件失败并可重试
分享 资源路由、权限重验、公开简介 分享入口、卡片字段、返回路径 不显示虚假的“已分享”；提供可用的官方入口方式
通知 站内消息、偏好、去重、事务事件 宿主授权、可用消息模板及发送条件 站内仍能查询结果，不阻断报名
隐私 目的、字段、保留期限、权利请求 宿主隐私声明及授权交互 未获可选权限时提供降级能力
学校与组织核验 组织代表权限、成员资格 校方实际允许的流程与接口 明确“未认证”，不伪造官方标识

**双端同一个人不能靠昵称合并。**建议将 provider + app_id + provider_user_id 对应到内部 user_id，微信与 QQ 的身份凭据各自验证。需要绑定时，用户证明对两个账号的控制权；遇到已经关联其他账户的冲突，停止自动合并并提供可申诉处理。原型没有真实绑定或账号合并实现。

10.2 建议架构，不是已经搭建的系统

前端候选是 uni-app + Vue 3 + TypeScript，或团队更熟悉且已验证双宿主的实现。uni-app 官方条件编译文档提供 MP-WEIXIN、MP-QQ 等平台区分方式；这只能支持“可组织共享与差异代码”的判断，不能证明每个 API、组件和当前审核能力都一致。正式锁定版本前须重做兼容验证。S4

后端建议从模块化单体开始，不需要先拆微服务：身份模块、社团模块、内容模块、活动模块、治理模块各自承载业务规则，基础设施只负责数据库、队列、对象存储和外部平台连接。业务用例不写进登录 SDK 或数据库连接文件。Go 可作为候选语言，最终依据团队掌握程度选择，不把它当成产品成功的前提。

微信小程序 ─ 宿主适配器 ─┐
                        ├─ 业务 API ─ 身份 / 社团 / 内容 / 活动 / 治理
QQ 小程序 ─ 宿主适配器 ──┘                  │
                                 关系数据库 + 私有对象存储
                                            │
                             审核服务 / 事务消息 / 操作审计

首版采用请求式 API 和可恢复的站内消息同步，不需要为了“社交”提前开发完整 WebSocket 聊天系统。缓存和队列按具体容量与任务需要引入，而不是架构图中越多越好。

10.3 开发时必须保留的模型与约束

模型 必要字段 / 关系 关键约束
User / Identity 内部用户、宿主类型、应用、宿主标识 宿主标识复合唯一；不以昵称作为账号键
Club / Membership 学校、组织、用户、状态、角色任期 一用户可属于多社团；每次请求重新判定当前资格
Content / Attachment 作者、社团、类型、可见范围、审核状态、版本 附件继承权限与生命周期；标题和缩略图也受保护
Comment / Reaction / Collection 内容、用户、状态 评论独立审核；点赞与收藏幂等；收藏私有
Knowledge / Revision 来源内容、维护人、版本、授权、归档 修改责任可追踪，避免过期知识持续误导
Event / Registration 起止、时区、名额、状态、规则；报名用户、状态 同人同活动唯一；确认名额受事务约束
Report / Appeal / Audit 对象、原因、处理人、结论、版本、时间 审核不能越权，冲突案件需独立复核
Handover 现任、继任、清单、状态、版本、有效期 一次性确认、资格重验、原子切换所有权

**建议的服务端契约：**读取列表先按资格和状态筛选，再分页与计算数量；禁止先返回全部数据，再让客户端隐藏。私有附件只向有权用户发短时访问凭据，过期、退出、下架后同步处理缓存与缩略图。日志不得携带完整凭证和不必要的个人信息。

报名确认在事务中检查活动状态和容量；用户-活动唯一约束加幂等请求键，避免重复点击和并发超卖。候补使用明确的排队顺序和邀请有效期；名额释放不等于对所有候补同时发确认。生产版自动递补需单独验收，原型只演示候补状态。

创建活动、取消活动、审核通过与消息生成应有一致性策略：例如在同一事务记录事件，再由后台工作器重试通知。消息可以迟到，业务状态不能因此回滚到错误值。所有有效期与排期使用服务端时间，业务时区明确为 Asia/Shanghai，不能信任用户设备时间。

10.4 API 草案与错误语义

下面是产品交付契约草案，不是已部署接口。

API 草案 权限 / 要做的事 典型返回与页面反馈
POST /auth/{host}/session 验证宿主临时凭证，建立内部会话 失效要求重新授权，不默认为入社
POST /clubs/{id}/applications 登录态、组织有效、无重复有效申请 待审核；重复则返回已有申请
POST /clubs/{id}/contents 成员有效、范围与授权、附件已归属本人 返回待审核内容 ID，不直接标记公开
GET /contents/{id} 按成员、作者、治理职责与发布状态鉴权 不存在/不可访问的外部表现避免泄露私域资源存在性
POST /contents/{id}/comments 评论资格、内容状态、防重复、频控 待审核或按正式治理规则处理
POST /events/{id}/registrations 成员资格、规则确认、容量、幂等 明确 confirmed / waitlisted，不能混同

未登录、无权限、名额/状态冲突、版本冲突、字段不合法、频率过高，应有独立业务错误码和用户可理解文案。网络错误保留输入；对破坏性操作先查询最终状态再重试。客户端只负责呈现与便捷校验，不能成为唯一规则执行者。

11 / MVP 与拓展：每加一项都要说明它强化哪个价值

层级 范围 本轮取舍
P0：验证价值与治理 运营方初始化少量社团；邀请、成员申请；统一发布、作品反馈；知识阅读/整理；免费活动；搜索；站内消息；本人记录；举报审核；换届 足以验证作品反馈和组织延续，不以所有 26 页完全独立研发估算工作量
P1：在留用之后强化 社内投票；自助建社审核；创作挑战；按贡献意愿匹配反馈伙伴；知识版本编辑增强；作者主动授权的作品集 原型已展示投票与建社提交；真实运行和规模治理仍未完成
P2：有明确需求再进入 校方授权系统对接；校友贡献；跨社协作；有权限的知识辅助检索 每项单独验证身份、隐私、维护人与运营成本
明确不做 陌生人私信、匿名表白墙、全校八卦、交易担保、付费知识市场、直播、完整小游戏平台、公开人气排行 这些方向不帮助当前最关键假设，反而引入新治理和商业问题

有价值的拓展，不只是“更多娱乐”

**半成品互助日：**社团发起一个主题，成员说明希望得到的帮助，愿意反馈的同伴主动认领。不要求必须交换点赞，避免虚假互动。

**从作品到方法卡：**作者在反馈后记录“我改了什么、为什么”，经其确认沉淀成带来源的知识条目。这会把一次社交转化为可检索的学习材料。

**小项目找搭子：**明确目标、预计时间、缺少的角色和合作约定，讨论仍发生在社内话题中。不默认公开联系方式，不让匹配系统自动创建私聊。

**毕业带走个人作品，组织留下获授权的经验：**个人作品集与组织资料是两个资产视角。毕业不等于创作者失去其作品控制，也不等于社团可以永久公开其所有内容。校友回访与查看范围通过新的成员政策确认。

AI 可以在以后帮助起草标题、整理知识、引用有权限的内容辅助检索；不能成为首版的价值前提，也不替代人类审核裁决。没有清晰授权与成本上限时，不批量拿私域内容送往外部模型服务。

12 / 冷启动与可验证的推进顺序

不承诺未经估工和平台审核的上线日期。以下按验收门推进，而不是按“画完多少页面”推进。

阶段 要完成什么 进入下一阶段的证据
G0：准入与需求 验证主体、平台类目、校方允许范围；开展访谈和能力小样 无明确准入阻断；发现可重复的反馈/知识痛点；组织者愿意担责
G1：小规模陪跑 选少量社团；每团一名负责人和若干自愿反馈伙伴；人工整理获授权的示例内容 不靠强制任务也能产生回应；成员能完成核心任务
G2：生产 MVP 接真实身份、权限、附件治理、活动一致性、申诉、备份与监控 安全和流程测试通过；治理责任人与反馈时效明确
G3：跨周期验证 至少观察足够成熟的留存队列，并演练换届和退出 新鲜感后仍有人回来；资料能被新人使用；管理不依赖一个人
G4：复制与商业试验 在相近组织复制，访谈实际预算方 每新增社团的支持成本可承受，有可验证的持续价值与付费理由

每团的种子内容建议只放真正有授权、能帮助新人的小规模材料：几份半成品、一篇社规、一份入门指南、一份上届经验、一次活动。不要用 AI 批量填满假动态，制造“大家都在用”的错觉。

邀请文案强调一个具体任务：“周五放映前，来给两份半成品留建议”，而不是“请大家下载支持社长”。原群仍保留即时通知；不抓取聊天记录，不强迫转发、加好友或授权通知换取参与资格。

13 / 如何判断做对了：指标与证伪条件

13.1 一个核心结果，两个配套判断

**核心指标建议：每周形成双向有效交流的成员数。**以去重内部用户为单位，统计同一自然周内，自己作出作品/知识/提问或有效回复等贡献，并与另一位成员形成真实回应关系的人数。排除机器人、自我回复、重复灌水；点赞不单独视为有效交流。跨社团汇总时再去重，不把成员关系数当用户数。

“有效”不能只用字数判断。初期抽样人工查看是否针对内容提供信息、建议或有意义的问题，并记录一致性；自动规则只能做辅助代理指标。这个指标也不是唯一价值：认真阅读但不发言的人可能同样获益，因此配套观察知识任务成功与留存。

13.2 埋点与数据口径草案

建议事件：invite_view、login_success、application_submitted、application_approved、content_submitted、content_published、feedback_published、feedback_viewed、knowledge_opened、knowledge_task_completed、event_registered、event_waitlisted、event_checked_in、handover_completed。

共同字段限定为事件 ID、去标识用户 ID、社团 ID、对象 ID、对象类型、业务状态、宿主、服务端时间、版本。不要在分析事件里上传私域正文、真实姓名、联系方式或完整搜索词。搜索分析可以记录有无结果、结果类型及去标识分类，特殊调查另走授权流程。

审批、发布、名额和交接以服务端成功事件为准，不以按钮点击量替代业务完成量。相同事件 ID 去重。所有队列、留存和时间窗采用相同业务时区，删除/失效关系的历史统计规则要由数据字典明确。

13.3 什么时候应该停止扩量

如果只有组织者在发布和回复，应先判断是否根本缺少成员需求，而不是再做积分。如果作品有浏览没有反馈，先改善反馈目标、同伴匹配与治理延迟。如果内容热闹但知识找不到，优先补整理与检索。如果活动只有强制参与者，不能据此声称社区留存成立。如果治理工时随内容快速上升、没有稳定负责人，暂停拉新。

14 / 商业模式与成本：先验证持续价值，再验证收入

首版建议核心参与免费，先不加入支付和复杂会员墙。后续可验证组织付费的明确工具价值，如多人治理、组织导出、合规审计、交接管理；或在获得校方授权后讨论组织级服务。这里是商业假设，不是已存在的采购意向和价格。

不建议一开始卖用户注意力或陌生人导流。商业活动必须明确标识与利益关系；不能把社团成员资料变成默认营销名单。若未来加入付费、交易、票务或赞助，需要重新核验平台类目、支付能力、责任和结算规则，不包含在当前 MVP。

成本模型应分开列：产品研发与测试、存储、图片/视频处理、下载流量、内容检查、人工审核、校内运营、客服、合规与备份。创作型社团的视频与工程文件可能改变成本结构，因此先限制支持的媒介类型和容量，再收集真实使用量。本次未获得云供应商报价，不给出看似精确的月成本。

基础判断式可以是：付费组织数 × 每组织净贡献 ≥ 固定运营与维护成本。净贡献需扣除该组织带来的存储、流量、审核和支持成本；不是把订阅收入直接当利润。对社团没有真实预算、校方采购周期不确定等情况，必须保留无法盈利的可能。

16 / 交付物、原型实现范围与测试说明
